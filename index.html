我怎么做事

比技能清单更能说明我会交付什么
01

先问约束，再谈方案

答案取决于真正的限制条件，而不是行业惯例。把标签和惯例先放一边，回到约束重推一遍，经常能推出不一样的结论。

02

端到端自己走完

从界面、数据、推理到打包发布，能自己走通的就不拆给别人。不是为了证明全栈，是因为穿过每一层才知道问题卡在哪一层。

03

用可复跑的门禁代替"感觉差不多"

写测试、设基线、做变异冒烟——先确认门禁真能抓到红，再信它给的绿。稳定性不靠观察几次，靠能重复触发。

04

把踩过的坑变成公共财产

遇到框架问题，先分清是我用法错了还是框架真有缺陷；确认是后者，就做成最小复现报上去，能修就修。

公开记录

都能点开核对，不是自我评价

PR #7101 · 补官方 async 文档缺失的两点MERGED

首帧更新要让出事件循环、后台线程异常的归属。维护者重写后合并，CHANGELOG 1.1.x 署名 @daneeller。这个 PR 还让维护者发现并修掉了一个真实的框架 bug（#7106，带 230 行测试）。

Issue #7109 · 异常日志记错 logger触发修复

用真实异常日志定位到 run_task() 的错误被记在 concurrent.futures 而非 flet logger，按 flet 过滤会完全漏掉。维护者在 1.x 复现后开了修复 PR #7110。

Issue #7107 · Page.update() 线程安全契约缺失

对照 0.86.5 和 1.x 源码逐行核实，指出线程安全契约从未被文档化，run_thread() 被普遍误读成"回 UI 线程"，实际进的是线程池。

Issue #7108 · schedule_update 跨线程不安全

1.x 调度器用 asyncio.Event.set() 跨线程调用不安全，已由社区贡献者认领修复。

也有我自己判断错了的时候：把日志末尾的 Session was garbage collected 当成崩溃原因，维护者指出那只是窗口关闭的 INFO 症状。用日志证据复核后我公开承认误判、修正结论——报告的价值不在于每次都对，在于能被证据纠正。
